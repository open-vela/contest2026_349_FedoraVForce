# 跨设备联动：板子通过局域网控制米家空调伴侣（miio）

> 设计说明，给 `~/vela-local` 里带采集器的会话从头实现用。协议已在主机上用 `miio.py` 验证（读状态 OK）。
> **这份文档和会话日志都会公开：不要在会话里打印、粘贴 token，不要写真实 IP，用下面的占位符。**

## 一、目标

在 launcher 里加一个「空调」应用：

1. 实时显示空调状态：开关、模式、设定温度、**实时功率**（W），每 2 秒刷新一次
2. 一个大按钮切换开关
3. 画板联动（可选，最后做）：画板打开「联动」开关后，手写识别出 `1` 开空调、`0` 关空调，结果卡上显示「已发送：开」

演示要讲的一句话：板子手写一个数字，TFLM 在板上识别，再通过以太网用 miio 协议控制另一台米家设备。

## 二、网络

```
板子 eth0 ──直连── 主机 ──NAT── 内网 ── 空调伴侣（Wi-Fi，UDP 54321）
```

- 板子的 IP、默认网关都是 defconfig 里写死的（`CONFIG_NETINIT_IPADDR` / `DRIPADDR`），网关就是直连的主机。主机已经开了转发和 NAT，**板子这边不用改网络配置**
- 已验证：板子 `ping <ac-ip>` 通，9–33 ms
- **不要执行 `ifconfig eth0 up`**：会触发 launcher 重启（已知问题）

## 三、配置文件（token 不进代码、不进 defconfig）

应用启动时读 `/tmp/miio.conf`（`/tmp` 是 tmpfs，掉电就没）：

```
<ac-ip>
<32 位十六进制 token>
```

- 这个文件**由人放到板上**（从主机用 TFTP `get`），会话里**不要 `cat`、不要打印**内容
- 读不到文件时，界面显示「未配置」，不要崩
- 解析时去掉行尾的 `\r` 和空白（用 TFTP 不带 `-b` 传会变成 `\r\n`，token 就会多一个字符）
- 调试输出里只打印 IP 和 device id，token 一个字符都不打

## 四、协议（已验证）

参考实现见同目录 `miio.py`（Python，约 60 行），C 版照着它写。

### 4.1 握手（hello）

发 32 字节：`21 31 00 20` + 28 个 `ff`，发到 `<ac-ip>:54321`（UDP）。设备回 32 字节：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 2 | magic `0x2131` |
| 2 | 2 | 长度 = 32 |
| 4 | 4 | 0 |
| 8 | 4 | device id（大端） |
| 12 | 4 | stamp（大端，设备侧的秒计数） |
| 16 | 16 | 新固件回全 ff 或全 0，不带 token |

### 4.2 命令包

```
key = MD5(token)            # token 是 16 字节二进制（32 位十六进制解出来）
iv  = MD5(key || token)
payload = AES-128-CBC(key, iv, PKCS7(JSON))
header  = 2131 | 32+len(payload) | 00000000 | device id | stamp+经过的秒数+1   （都是大端）
packet  = header[0:16] || MD5(header[0:16] || token || payload) || payload
```

- JSON：`{"id":<递增整数>,"method":"<方法>","params":[...]}`，紧凑格式（不要空格）
- 回包结构相同：去掉前 32 字节，用同样的 key、iv 解密，去掉 PKCS7 填充，再去掉末尾的 `\0`，就是 JSON
- `id` 每条命令递增；回包里的 `id` 要和请求一致，不一致就丢掉
- stamp：每次握手重新取一次最省事（每条命令前都 hello 一次，开销很小）

### 4.3 空调伴侣 2（`lumi.acpartner.mcn02`）的命令

| 方法 | params | 回包 `result` | 状态 |
|---|---|---|---|
| `miIO.info` | `[]` | 对象，含 `model`、`fw_ver` 等；**也含 token、mac、ap，不要打印整个对象** | ✅ 已验证 |
| `get_prop` | `["power","mode","tar_temp","far_level","ver_swing","load_power"]` | 例：`["on","cool",25,"","on",202.00]` | ✅ 已验证 |
| `set_power` | `["off"]` | `["ok"]` | ✅ 已验证：功率 283 W → 96 W（4 s）→ 24 W 待机（16 s） |
| `set_power` | `["on"]` | `["ok"]` | ✅ 已验证（人看实物确认空调开了）。米家里开了**速冷**，开机后设定温度会变成 20°C；这是用户设置，不要用 `set_tar_temp` 改回去（10-30 实测：开机后立刻设回 25，十几秒内又被速冷改成 20）。开机后功率可能一直很低（25–28 W）：室温已经低于设定温度时压缩机不启动，这不代表没开 |
| `set_tar_temp` | `[25]` | `["ok"]` | ✅ 回 ok，`get_prop` 里 tar_temp 变回 25 |

`load_power` 是空调当前功率（W，浮点数）。

**空调伴侣的工作方式（决定了界面怎么做）**：它是带计量的插座 + 红外发射器。控制空调靠模仿遥控器发红外，每一帧都是完整状态（开关、模式、温度、风速、扫风）。红外是单向的，所以 `power / mode / tar_temp` 是**空调伴侣自己记的状态**，不是从空调读回来的；只有 `load_power` 是实测。因此：

- 发「开」之后不改温度，速冷设的 20°C 如实显示，要别的温度让人用界面调
- 界面上「是否真的在制冷」用 `load_power` 判断，不要只看 `power` 字段
- 关机后再开，空调一般有约 3 分钟的压缩机保护，这段时间功率低是正常的；界面上可以提示「等待压缩机启动」

### 4.4 现场演示要换设备：协议库要通用

办公室这套（空调伴侣 + 主机 NAT + 内网）到决赛现场都没有。现场打算用：**便携路由器（LAN 设成和板子同网段，网关是 `.1`）+ 米家 Wi-Fi 智能插座 + 台灯**，不依赖场地网络。空调这条用来录提交视频。

所以：

- `app/miio/` 只管协议（hello / 加解密 / 发 JSON / 收 JSON），**不认识任何具体设备**
- 「设备型号 → 读状态用什么方法和参数、开关用什么方法、结果怎么解析」做成一张小表，空调伴侣是第一行，插座以后加一行
- 新款 MIoT 设备用 `get_properties` / `set_properties`，参数是 `[{"did":"<did>","siid":2,"piid":1,"value":true}]` 这种格式；老款 miio 设备（包括空调伴侣）用 `get_prop` / `set_power`。表里两种都要能表达
- `miio.conf` 加一行设备型号（第三行，可选，缺省按空调伴侣处理），界面根据型号显示对应的字段
- 插座的具体型号和 siid/piid 等设备到了再定，**先不要猜**

### 4.5 演示模式（mock，现场兜底）

现场网络不可控，板上要能**完全离线**演示同一套界面和交互。做法：

- 设备操作抽成一个后端接口：读状态、开关、设温度。两个实现：
  - `miio`：真设备，走第四节的协议
  - `mock`：板上内存里的模拟空调，不走网络
- 选择规则：
  - `/tmp/miio.conf` 存在 → `miio`
  - 文件不存在 → `mock`
  - NSH `miio mode real|mock` 可以强制切换（现场网络时好时坏时用）
- **诚实标注**：`mock` 模式下，空调页面和画板结果卡上一直显示醒目的「演示模式 · 模拟设备」标签，NSH 输出也带 `[mock]`。不允许出现「看起来像真设备、其实是模拟」的画面
- mock 的行为照真机实测（10-29）来，这样界面逻辑和真机一致：
  - 关机：功率先 ~96 W，约 15 s 后降到 ~24 W 待机
  - 开机：**设定温度变成 20°C**（真机开了速冷就是这样，界面要能如实显示）；前 ~20 s 是压缩机保护，~30 W；之后 `120 + (30 − 设定温度) × 30` W（25°C ≈ 270 W），上下抖 ±3 W
  - 每次操作随机延迟 50–150 ms，模拟网络往返，保证「网络放在自己线程里」的结构在 mock 下也被用到
- mock 和真机共用状态解析和界面代码，只有后端不同

验收（mock）：拔掉网线、不放 `miio.conf` 重启 → 空调页显示「演示模式」；开、关、设温度都能用，功率曲线按上面的规律变；插回网线、放好 `miio.conf`、执行 `miio mode real` → 切到真设备，标签消失。

## 五、实现建议

### 5.1 结构

- `app/miio/`：协议库（hello、send、recv、加解密）+ NSH 命令 `miio get | on | off`，**先做命令行，跑通再做界面**
- `app/aircon/`：LVGL 应用页面，按现有 `app/monitor` 的写法接进 launcher（磁贴 + 启动方式保持一致）
- 画板联动：在 `app/paint` 里加一个开关，识别结果交给 `miio` 库，不要在 paint 里复制协议代码

### 5.2 用现成的库

- AES-128-CBC：`apps/crypto/mbedtls`（`mbedtls_aes_setkey_enc/dec` + `mbedtls_aes_crypt_cbc`）；MD5 用 mbedtls 的，或板上已开的 `CONFIG_CODECS_HASH_MD5`
- JSON：`apps/netutils/cjson`，或者回包格式固定、用 `sscanf` 解析也行，选简单的
- 不要自己实现 AES；不要拷贝 python-miio（GPL）的代码，按协议说明自己写

### 5.3 线程与超时

- 网络收发放在**应用自己的线程**里，LVGL 线程只读结果、刷新界面；不要在 LVGL 回调里阻塞等 UDP
- **不要用系统工作队列（lpwork / hpwork）跑网络请求**：10-29 上板遇到过一次 lpwork 断言（`nxmutex_wait` 里 `DEBUGASSERT(!up_interrupt_context())`），根因还没查清，别再往工作队列里加负担
- UDP 收包超时 2 秒，失败重试 1 次；连续失败时界面显示「离线」，恢复后自动重连
- 2 秒轮询一次 `get_prop`；按下开关后立即读一次状态，确认生效

### 5.4 配置

- Kconfig：`CONFIG_..._MIIO`，`select` mbedtls 的 AES / MD5（以 menuconfig 实际结果为准，改完 `git diff` 看 savedefconfig 有没有删东西）
- 设备 IP、token 都**不进 Kconfig**，只从 `/tmp/miio.conf` 读

## 六、验收

1. NSH：`miio get` 打印 power / mode / tar_temp / load_power，和主机上 `miio.py ... get_prop` 一致
2. `miio.conf` 缺失或 token 错误：给出明确报错（token 错时设备不回或解密失败），不崩
3. 空调页面：数值 2 秒刷新；拔掉网线，10 秒内显示「离线」；插回自动恢复
4. ⏳ 开关（等人确认可以动空调）：按钮开 → 关 → 开，每次状态都在 4 秒内反映到页面
5. ⏳ 画板联动：写 `1` / `0` 各 5 次，记录成功次数
6. 跑 10 分钟：launcher 不卡，`free` 不持续下降，无断言

## 七、会话里的注意事项

- token：不打印、不粘贴、不写进任何文件或提交信息；需要配置板子时，请人来放 `/tmp/miio.conf`
- IP：文档、代码、提交里都用 `<ac-ip>` 之类的占位符
- 上板流程照 `notes/CONNECT.md`；telnet 可以代替串口登 NSH（串口偶发接收卡死，原因待查）
- 动空调（`set_power`）前先问人
